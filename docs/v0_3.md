# FinCore v0.3

This document collects the changes of language v0.3 against v0.2
(docs/v0_2.md, which in turn amends fincore_language_specification_v0_1.md).
The binding decisions are numbered in docs/semantics_decisions.md under
"v0.3" (140–157).

v0.3 is the first language version implemented only in the self-hosted
compiler (`compiler/`, `LangVersion = "0.3"`); finc0 stays frozen at v0.2
(bootstrap/README.md, decision 139). compiler/ itself does not use the
v0.3 features yet: it may once a `v0.3.0` tag exists and `bootstrap/SEED`
has been bumped to it. Every test of a v0.3 feature carries
`// SINCE: v0.3` (testdata/README.md), so finc0 and the seed skip it.

v0.3 adds three things:

1. the predeclared functions `min` and `max`;
2. `match` on `[]byte` values with string patterns (string scrutinees were
   already matched by v0.2; their rules are restated here);
3. multi-value `match` expressions:
   `return match v { Int(h, l) -> h, l, true; _ -> 0, 0, false }`.

## `min` and `max`

```go
const Lo = min(7, 3, 5)              // untyped constant 3
const Width u32 = max(u32(4), 9, 2)  // typed constant 9
var table [max(2, Lo)]u32            // array length

func clamp(x u32, lo u32, hi u32) u32 {
	return max(lo, min(x, hi))
}

func first(a string, b string) string {
	return min(a, b)
}
```

### Universe (spec 2.4)

`min` and `max` are predeclared functions of the universe block, like
`len`. They are shadowable: a package-level or local declaration named
`min` or `max` (a function, constant, variable or parameter) hides the
builtin in its scope, so programs written for v0.2 that declare their own
`min`/`max` keep their meaning (`testdata/pass/pass_minmax_shadow.fc`,
which has no SINCE and also runs on finc0; compiler/build.fc has
parameters named `min` and `max`). Struct fields are not affected (they
are not in any scope).

### Rules

- **Arity.** Two or more operands (variadic). Fewer is E2003
  `not enough arguments in call to min: have 1, want at least 2`.
- **Typing** follows the comparison operators (`<`):
  - If some operand is typed, its type T is the type of the call: every
    other typed operand must have type T (E2002 `mismatched types u32 and
    u64 in call to max`, at the operand) and every untyped constant is
    converted to T (E2002 `constant 300 overflows u8`, `cannot use "a"
    (untyped string constant) as type u32`).
  - If every operand is an untyped constant, their kinds must agree
    (E2002 `mismatched types untyped int and untyped string in call to
    min`); untyped int and untyped char mix to untyped char, as for
    comparisons. The result is an untyped constant of that kind, typed by
    its context like any untyped constant (`const Small u8 = min(300, 2)`
    is 2; `max(3, 256)` as a `u8` is E2002 `constant 256 overflows u8`).
  - T must be ordered: an integer type or a string type (named types
    included). Otherwise E2002 `invalid argument a for max (type bool is
    not ordered)` (at the first operand; also for untyped bool and nil).
  - An operand of type-parameter type is E2011 `min inspects a value of
    type parameter type T` (generic code may not inspect values, as for
    the comparison operators).
- **Constants.** If every operand is a constant, the call is a constant
  (folded at check time): the first least (greatest) operand. It may
  initialize constants, size arrays and appear in other constant
  expressions. Otherwise the call is a value of type T.
- **Values only.** `min`/`max` must be called (E2002 `builtin min must be
  called`); there is no spread form.
- **Effects.** Total: allowed in every function kind, including
  `comptime` functions, where the interpreter evaluates them.
- **Totality.** A call of `min`/`max` whose operands are loop-invariant
  is loop-invariant, so `for i := u32(0); i < min(n, 10); i++` is a T1
  loop (decision 144).

### Lowering

A constant call is emitted as its folded value (`const Lo = 3`,
`var table [3]uint32`, `x + -5`). Other calls use Go's predeclared `min`
and `max` (Go ≥ 1.21; the module's go.mod requires a newer Go):

```go
func clamp(x uint32, lo uint32, hi uint32) uint32 {
	return max(lo, min(x, hi))
}
```

User declarations named `min`/`max` are emitted as `_fc_u_min` /
`_fc_u_max` (as every Go predeclared name, v0.1), so the Go builtins are
never shadowed in the generated code.

## Matching strings and `[]byte`

```go
const Get = "GET"
const Put string = "PUT"

func method(b []byte) u32 {
	return match b {
		Get | "HEAD" -> 1
		Put -> 2
		"" -> 9
		_ -> 0
	}
}

func route(m string, p []byte) u32 {
	return match (m, p) {
		("GET", "/") -> 1
		(_, "/admin") | ("DELETE", _) -> 3
		_ -> 0
	}
}

if !(t is Word(w)) || w is "skip" { ... }
```

### Rules

- **String positions** (v0.2, unchanged): a pattern position of a string
  type accepts string literals and string constants assignable to that
  type (Go assignability: a constant of a named string type does not
  match a plain `string` position). Values are compared with `==`.
- **`[]byte` positions** (new): a pattern position whose type has the
  underlying type `[]u8` (`[]byte`, or a named byte slice type such as
  `type Buf []byte`) accepts **string literals and constants of any
  string type** (untyped, `string`, named string types). The pattern
  matches a slice with exactly the same bytes; a nil or empty slice
  matches `""`. Other literals are still E2002: `nil` (`cannot match
  values of type []u8 against literals`), integers (`cannot use 65
  (untyped int constant) as type []u8`). Decision 146.
- **Everywhere.** Both forms are allowed in every pattern position: the
  top level, tuple elements, enum payloads (`Word("if")`), or-pattern
  alternatives, `@` operands (`w @ "GET"`), guards' arms, and `is`
  (`b is "GET" | "HEAD"`, let-else, `&&` chains). Bindings of a `[]byte`
  position bind the slice (borrowed, origin of the scrutinee, v0.2).
- **Usefulness.** Strings and byte slices are infinite literal domains:
  a match expression needs `_` or a binding (E2012 `non-exhaustive match
  expression on []u8: missing '_' arm`); a match statement need not be
  exhaustive (no arm runs). A literal or constant equal by value to an
  earlier one is unreachable (E2012 `unreachable pattern: duplicate case
  Get`), also across literal/constant spellings.
- **Comptime** compares a byte slice value with the pattern's bytes.

v0.2 accepted a string *constant* pattern on a `[]byte` scrutinee in the
type checker but emitted Go that does not compile (`case "hello":` in a
switch on a `[]uint8`); v0.3 defines and lowers it.

### Lowering

Deterministic, without allocation (Go compiles `string(b)` in a
comparison or a switch tag to a byte comparison):

- A flat match (no guards, tuples or bindings that need an if chain)
  whose scrutinee is a byte slice is a Go switch on the string
  conversion; case values are string literals (constants folded):

  ```go
  switch string(b) {
  case "GET", "HEAD":
  	return 1
  case "PUT":
  	return 2
  ...
  ```

- Everywhere else (if chains, tuple elements, payloads, `is`), a test on
  a byte slice path is `string(path) == "..."`:

  ```go
  if _fc_t0._tag == 0 && string(_fc_t0._0_0) == "for" {
  ```

String positions lower as in v0.2 (`switch s {`, `s == "x"`).

## Multi-value `match` expressions

```go
func split(v Val) (u32, u32, bool) {
	return match v {
		Int(h, l) -> h, l, true
		_ -> 0, 0, false
	}
}

func flags(n u32) (u8, bool) {
	return match n { 0 -> 255, false; 1 -> 1, true; _ -> 2, n > 10 }
}

a, b := match k {
	0 -> h, true
	_ -> pair(h) // a call with two results
}
small, name = match h { 1 -> 200, "one"; _ -> 1, "other" }
```

### Grammar (diff against docs/v0_2.md, "Patterns")

```ebnf
MatchExpr  = "match" Scrutinee "{" ExprArm { ( ";" | "," ) ExprArm } [ ";" | "," ] "}" .
ExprArm    = Patterns [ Guard ] "->" ArmValues .            (* was: "->" Expr *)
ArmValues  = Expr { "," Expr } .                            (* new *)
```

`,` is both the separator of an arm's values (new) and, since v0.2, an
optional separator of the arms of a match expression
(`match c { Red -> 1, _ -> 2 }`). The parser decides each `,` that
follows a value of an arm:

- it **ends the arm** if the next token is `}` (a trailing separator), or
  if the tokens after it, up to the end of the arm — the next `;`
  (explicit or automatic at a newline) or the `}` closing the match, at
  bracket depth 0 — contain `->` at bracket depth 0, i.e. they form
  another arm;
- otherwise it **continues the arm's value list**.

So every v0.2 match expression parses as before (after an arm-separating
`,` there is always `}` or a whole arm with its `->`), `Red -> 1, Green
-> 2` still has two arms, and `Int(h, l) -> h, l, true` has one arm with
three values. A match with multi-value arms must therefore separate its
arms with `;` or newlines: in `match k { A -> 1, 2, B -> 3, 4 }` the
second `,` is read as an arm separator and `2, B -> ...` is not an arm
(E1001 `expected '->', found ','`). A value list may continue on the next
line after a `,` (no automatic `;` follows a `,`). Brackets, braces and
parentheses nest, so values may be calls, struct literals, function
literals and nested match expressions. The decision needs unbounded
lookahead over tokens, which the parser has (the whole token array);
the grammar is otherwise unchanged and there is no backtracking.

AST: a multi-value arm's `Expr` is a `TupleExpr{Elems}` (the node of
tuple scrutinees, v0.2) positioned at its first value; a single value is
the expression itself, as before.

### Where a multi-value match may appear

A match expression is **multi-value** if one of its arms is a value list
(two or more values), or if it is in a multi-value context and one of
its arms is a single expression that gives several values (a call with
several results or a nested multi-value match). Otherwise it is an
ordinary v0.2 match expression with v0.2 rules and messages.

The multi-value contexts are those of Go's multi-value calls with a
single right-hand side:

- `return M` in a function with N ≥ 2 results;
- `x1, ..., xN := M` and `x1, ..., xN = M` (targets may be `_`; `:=`
  may redeclare);
- an arm of a multi-value match (nested matches get the same context).

Anywhere else a multi-value match is E2003 `multiple-value match
expression (2 values) in single-value context` (including `const`
initializers, call arguments and operands). A multi-value match is never
a constant (Go has no multi-value constants); in `comptime` functions it
is evaluated by the interpreter.

### Typing (decision 151)

- **Count.** Every arm gives the same number N of values, the count of
  the first arm with several: a value list of N expressions, or one
  expression with N values. Otherwise E2003 `match arm has 3 values, want
  2` / `match arm has 1 value, want 2` (at the arm's value).
- **Types per position.** For each position i the values of all arms
  agree like the arms of a v0.2 match expression: typed values must have
  identical types (E2002 `match arm value 2 has type u32, want bool`, at
  the value), untyped constants take that type. If position i is an
  untyped constant in every arm, it takes the type the context expects at
  i — the function's i-th result type, or the type of an existing
  variable assigned by `=`/`:=` — and otherwise (new variables, `_`) its
  default type; untyped int and untyped char mix to untyped int (as for
  match arms), and a position that is untyped nil everywhere without a
  context type is E2004 `use of untyped nil in match`. Each value must be
  representable in its type (E2002 `constant 300 overflows u8`).
- **Result.** The match has the tuple type (T1, ..., TN). The usual
  checks of multi-value calls follow: `wrong number of return values:
  have 2, want 3`, `cannot use result 2 of type bool as type u32 in
  return statement`, `assignment mismatch: 2 variables but match
  expression returns 3 values`, `cannot assign value of type u32 to
  variable of type bool`.

### Other passes (decision 152)

- **Scope.** The origin of a multi-value match is the join over all
  arms and all positions (as the origin of a multi-result call is that of
  all its results); every target of an assignment gets it. Returning a
  value that refers to a local through any position is E3002
  (`testdata/fail/fail_match_multi_scope_escape.fc`).
- **Linearity.** Each value that is a Linear variable is moved into the
  result, exactly like a single-value arm or the right-hand side of an
  assignment: `c, n := match k { 0 -> conn, 0; _ -> conn, k }` moves
  `conn` into `c`; using `conn` afterwards is E3003.
- **Totality.** Arms are branches. Variables assigned from a multi-value
  match get no facts (like the results of a multi-result call); patterns
  give none either (decision 79).
- **Comptime.** The selected arm's values are evaluated left to right
  and copied into a tuple value, which `return` and multi-value
  assignment unpack.

### Lowering (decision 153)

- `return M` in a function with N results, outside `scope` blocks, is
  lowered in place, like v0.2's single-result `return match`: the switch
  or if chain is emitted and every arm returns its values
  (`return h, l, true`); an arm that is a call returns it
  (`return pair(h)`), a nested match recursively.

  ```go
  func split(v Val) (uint32, uint32, bool) {
  	switch v._tag {
  	case 0:
  		h := v._u32_0
  		l := v._u32_1
  		return h, l, true
  	default:
  		return 0, 0, false
  	}
  }
  ```

- `:=` and `=` use an immediately called function literal with N results
  (Go allows a multi-value call on the right-hand side):

  ```go
  small, name = func() (uint8, string) {
  	switch h {
  	case uint32(1):
  		return 200, "one"
  	default:
  		return 1, "other"
  	}
  }()
  ```

- `return M` inside a `scope` block evaluates the function literal into
  temporaries, waits for the scopes and returns them (as for multi-result
  calls in v0.1).

Both forms are deterministic; untyped values are emitted with the types
fixed by the checker. A literal costs a call that Go may inline; a
statement-level lowering of `:=` (declaring the targets and assigning in
the arms) was not chosen because `:=` may redeclare and the targets may
be `_`, which the function literal handles for free.

## Failure report of `main`

Decision 156. A non-nil error from `driver func main` still exits with
status 1, but the runtime prints `error: <err>` only if the program has
not written to stderr. A program that wrote to stderr (`io.WriteStderr`)
has reported the failure itself:

```text
$ finc check bad.fc            # v0.2: a third line `error: fincore: invalid number`
bad.fc:4:6: error[E1001]: compound assignment operator >>= is not supported; write c = c >> 1
$ echo $?
1
```

This is a runtime change (runtime/fincrt), not a language feature: it
needs no `// SINCE:` and applies to every program built against the v0.3
runtime, including the bootstrap's stage 1 built by the seed. The emitted
Go is unchanged.

## Limitations

- `,` cannot separate the arms of a match with multi-value arms; use `;`
  or newlines.
- Multi-value matches are not allowed as call arguments (`f(match ...)`
  with several values), in `var` declarations (one name only) or as
  constants.
- Variables assigned from a multi-value match get no totality facts (pass
  the measure expression itself to recursive calls).
- `:=`/`=` from a multi-value match cost a function literal call.
- min/max have no spread form; they are not generic over type parameters
  (E2011).
- Byte-slice patterns compare whole slices; there are no prefix patterns.
